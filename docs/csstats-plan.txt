## Goal

A service that runs while I play CS2 and, without me ever touching a
replay file:

1. Discovers finished Premier/Competitive matches from my Steam match
   history.
2. Resolves each sharing code to a replay URL via a dedicated Steam
   bot account and the CS2 Game Coordinator, in Python.
3. Downloads and parses the replay for detailed events.
4. Stores canonical data in SQLite.
5. Deletes the temporary replay after successful processing.
6. Recovers missed or interrupted matches after restarting.
7. Answers long-term trend questions by SQL against SQLite.

Game State Integration is a latency optimisation only, added last.
History polling alone must be sufficient for a complete, correct
dataset.


## Non-Negotiable Constraints

- SQLite is the single source of truth. There is no export layer in

- Nothing is mocked until a real payload of that shape has been
  captured as a fixture.
- Dependency versions are pinned by me, not chosen by you. Ask if a
  version is unknown.
- Every phase ends with a working CLI command I can run.

Concurrency decision (settle here, do not revisit later)

steam is built on gevent, not asyncio. Gevent's monkey-patching does
not coexist cleanly with asyncio in one process. Therefore this
project is gevent-based end to end:

- Use requests for HTTP, not httpx or aiohttp. It monkey-patches
  cleanly.
- When Phase 8 adds the GSI listener, use gevent.pywsgi, NOT aiohttp.
  Do not add asyncio anywhere.
- Call gevent.monkey.patch_all() once, as the very first statement of
  the entry point, before any other import.

One process, one concurrency model, no subprocess boundary, no
inter-process protocol. This is the main prize for going pure Python.
Do not give it back.

Protocol reality

request_full_match_info does not return a value; the response arrives
as a full_match_info event. So:

- Resolve one share code at a time. Correlate by in-flight request,
  not by ID.
- Apply a hard per-request timeout. A timeout means the event never
  arrived, so mark the attempt failed and advance the queue.
- Expect the GC to drop the connection periodically. Detect not ready
  and re-launch before the next request rather than assuming a
  persistent session.

Fallback (only if 0b fails - report to me first, do not act
unilaterally)

If the forked csgo package cannot connect to the CS2 GC, the fallback
is a Node subprocess using steam-user + globaloffensive, communicating
over newline-delimited JSON on stdin/stdout, with diagnostics on
stderr. In that case the Python side reverts to asyncio and httpx, and
the GC worker is the only JavaScript in the repository. Do not
pre-emptively build for this.

Do NOT use boiler-writter as the fallback. It works through the local
logged-in Steam client and briefly launches CS2 in the background,
which conflicts directly with the requirement that this service runs
while I am playing CS2.

====================================================================
PHASE 2 - MATCH DISCOVERY
====================================================================

Use Valve's ICSGOPlayers_730/GetNextMatchSharingCode/v1.

Maintain a durable cursor. For each returned sharing code:

1. Insert a unique ingestion job.
2. Advance the cursor transactionally in the same commit.
3. Continue until Valve returns no newer code.
4. Never lose later matches because one replay is delayed or
   unavailable.

Handle: HTTP 202 with nextcode: n/a, invalid API or history
credentials, invalid starting codes, HTTP 429 and 503 with exponential
backoff and jitter, network timeouts, duplicate sharing codes, and
many matches discovered at once after downtime.

DELIVERABLE: python -m csstats discover populates the job table from
real history and is safely re-runnable.


====================================================================
PHASE 3 - GC RESOLVER (productionise the spike)
====================================================================

Promote the Phase 0 spike into a proper in-process module. One
long-lived SteamClient and CSGOClient owned by a single gevent
greenlet, exposing one synchronous-looking method:

    resolve(share_code) -> ResolveResult(ok, demo_url, raw, error_kind)

error_kind is one of: gc_timeout, gc_unavailable, login_failed,
no_match_info, no_replay_url, malformed. The caller maps these onto
job statuses; the resolver itself never touches the database.

Requirements:

- Persist and reuse Steam session state (login_key / refresh token) on
  disk, gitignored, so full re-login is rare.
- Generate Steam Guard codes from the TOTP secret via
  SteamAuthenticator. Never prompt interactively.
- Serialise resolutions with a lock. One in flight at a time, per
  Phase 0.
- Detect GC disconnection and re-launch() before the next resolution
  rather than assuming a persistent session.
- Handle login challenges, rate limiting, CM disconnects, malformed
  messages, and clean shutdown on Ctrl+C.
- Return the full raw GC payload alongside the extracted URL and
  persist it, so reprocessing a match never needs a second GC call.
- Never perform trading, inventory modification, matchmaking, or
  gameplay automation.
- Decode share codes with the Phase 0a implementation. No JavaScript,
  no external service.

DELIVERABLE: python -m csstats resolve <sharecode> prints a demo URL,
returns a clean typed failure for an expired code, and survives being
run twenty times in a row without re-logging in.


====================================================================
PHASE 4 - DOWNLOAD, PARSE, PERSIST
====================================================================

Job lifecycle

    discovered
    awaiting_gc
    awaiting_publication
    downloading
    parsing
    persisting
    complete
    retryable_failure
    expired            (terminal - replay no longer obtainable)
    permanent_failure  (terminal - everything else)

Store attempt count, timestamps, next retry time, and sanitised error
details.

Replay availability window (hard requirement, not an edge case)

Valve replays are NOT available the moment a match ends. Publication
commonly takes several minutes and occasionally does not happen until
much later. Valve then deletes them after roughly one to two weeks.

Therefore:

- awaiting_publication must poll with a generous configurable deadline
  (default 24 hours), not a five-minute give-up.
- A job whose publication deadline passes, or whose demo URL returns
  404/410/expired, transitions to expired, never to
  retryable_failure. Expired is a normal outcome and must not trigger
  retry storms or look like a bug in the logs.
- On startup, warn loudly if any job has been sitting in awaiting_gc
  or awaiting_publication for longer than the retention window, since
  those matches are permanently lost.

Download

Timeouts, bounded retries, content-type and minimum-size validation,
BZ2 decompression, temporary filename then atomic rename, cleanup
after successful persistence, quarantine for corrupt files with
configurable retention.

Parsing

Use only field names present in fixtures/demoparser_schema.json.
Identify players by SteamID64, never by display name. Exclude warmup
activity and team damage from competitive metrics while storing the
raw flags that allow later recalculation.

Store raw event rows for: kills, damage, weapon fire, purchases,
grenades, flashes, bomb events. Capture per-event match ID, round
number, tick, match clock, attacker/victim SteamIDs, names at match
time, team and side, weapon, hit group, damage, health and armour
damage, headshot/wallbang/smoke/blind flags, positions, assister,
flash assister, equipment information, grenade origin and destination,
bomb site and action, and round-winning reason.

Do not collect chat or voice data. Position sampling is deferred to
v2. No stat in Phase 5 needs it, and it is the largest table by an
order of magnitude.

Idempotency

A restart during downloading, parsing, or persistence must resume
without duplicate matches or partial statistics. Enforce uniqueness on
match ID and on event identity fields. Wrap all persistence for one
match in a single transaction. Store timestamps in UTC.

Tables for v1: schema migrations, tracked players, history cursor,
ingestion jobs, matches, match players, rounds, kills, damage, weapon
fire, purchases, grenades, flashes, bomb events, player-match
statistics, player-round statistics, clutch attempts.

DELIVERABLE: python -m csstats sync --once takes an empty database to
fully populated raw event data, and is safe to interrupt and rerun at
any point.

PHASE 5 - DERIVED STATISTICS
====================================================================

Calculate and document the formula for each of:

Kills, assists, deaths; K/D as total kills over total deaths; K/A/D
per round; ADR as actual enemy health damage over rounds played;
headshot kill percentage; CT/T splits; win rate; opening kills and
deaths; opening-duel success rate; trade kills and traded deaths;
KAST; multikill rounds; utility damage; enemies flashed and enemy
blind duration; economy spending and equipment value; per-map
performance.

Trade window: five-second documented default, with raw timestamps
preserved so it can be recomputed.

Clutch attempt: a player becomes the only living member of their team
against at least one living opponent. Record starting opponent count,
starting tick, side, kills during the attempt, bomb state, round
result, and whether it was won.

Do not invent an overall rating or claim to reproduce HLTV Rating 2.0.

Testing (this is the phase that must not be under-tested)

Build hand-calculated fixtures from one real parsed demo. I will
verify a subset by hand against the in-game scoreboard. Then test
every metric, plus: clutch detection 1v1 through 1v5, trades, KAST,
overtime, side switching, zero-kill and zero-death players, ties, and
truncated or incomplete demos.

DELIVERABLE: python -m csstats stats <match_id> prints a scoreboard
that matches the in-game scoreboard exactly.

PHASE 8 - GSI (optional latency optimisation)
====================================================================

Only after Phase 7 is stable and proven.

- python -m csstats install-gsi locates the CS2 installation via Steam
  configuration/registry data and installs
  gamestate_integration_csstats.cfg pointing at a localhost endpoint
  with an auth token.
- A local gevent.pywsgi listener (not aiohttp, per the Phase 0
  concurrency decision) requesting only: provider identity, map and
  game mode, match phase, round state, phase countdowns, local player

- On gameover, trigger an immediate history check instead of waiting

- Handle duplicate and out-of-order payloads idempotently. If CS2
  closes mid-match, do nothing special. History polling will catch it.

GSI is never a statistics source and must never be able to create a
